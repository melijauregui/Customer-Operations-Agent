# V2 — Explicit workflows with LangGraph

## Goal

Replace the manual `while` loop from V1 with an explicit state graph built
directly with LangGraph.

V2 is meant to teach the core workflow concepts behind agent orchestration:

- shared graph state;
- nodes with clear responsibilities;
- fixed and conditional edges;
- loops with termination conditions;
- conversation checkpoints;
- explicit separation between model decisions, tool execution, result
  verification, and business logic.

The goal is not to add new Customer Operations capabilities. The same four
order tools and HTTP behavior from V1 should continue working while the
internal orchestration becomes explicit, inspectable, and testable.

## Why LangGraph is introduced now

The V1 agent already behaves like a small state machine:

```text
call model
    ↓
tool calls?
  ├── no  → final response
  └── yes → execute tools → call model again
```

V1 implements that state machine with a bounded Python `while` loop. V2 keeps
the same behavior but represents it with LangGraph primitives instead:

```python
StateGraph
START
END
nodes
edges
conditional edges
checkpointer
```

LangGraph is not required for an agent this small. It is introduced as a
learning step and as infrastructure for later features such as durable
execution, human approval, resumable workflows, and more complex routing.

## New dependency

V2 adds:

```text
langgraph
```

The project will use LangGraph's low-level Graph API directly. It will not use
high-level abstractions that build the agent loop automatically.

Initially, V2 will not use:

- `create_react_agent`;
- the prebuilt `ToolNode`;
- `ChatOpenAI`;
- LangSmith;
- LangGraph Platform or Agent Server;
- PostgreSQL or Redis checkpointers;
- interrupts or human-in-the-loop;
- subgraphs or multi-agent orchestration.

The existing `AsyncOpenAI` client, JSON tool schemas, Pydantic argument models,
and custom tool dispatcher remain visible and under application control.

## Proposed architecture

```text
POST /chat
    ↓
main.py
    ↓
agent.handle_message(...)
    ↓
LangGraph workflow
    │
    ├── call_model
    │      └── AsyncOpenAI + tool schemas
    │
    ├── execute_tools
    │      └── Pydantic validation + trusted customer_id injection
    │
    └── verify_results
           └── deterministic validation of tool outputs
                    ↓
             tools/orders.py
             business logic
```

FastAPI will continue to depend only on the application's own
`handle_message(...)` interface. LangGraph remains an internal orchestration
detail, which makes it possible to replace it later without changing the HTTP
contract or the order tools.

## Graph flow

```text
START
  ↓
call_model
  │
  ├── final text ─────────────────→ END
  │
  └── one or more tool calls
               ↓
         execute_tools
               ↓
         verify_results
               │
               ├── valid results ─────────────→ call_model
               └── invalid internal result ───→ safe failure → END
```

The graph may go through several `call_model → execute_tools →
verify_results` cycles when a later tool call depends on the result of an
earlier one.

## Graph state

The workflow will use a small typed state object. A conceptual version is:

```python
class AgentState(TypedDict):
    messages: Annotated[list, message_reducer]
    customer_id: int
    tool_iterations: int
    verification_error: str | None
```

### `messages`

Contains user, assistant, and tool messages. New messages are appended through
a reducer instead of replacing the complete history.

### `customer_id`

Trusted request or session context. It is never generated by the model and is
injected by the application when a tool is executed.

### `tool_iterations`

Tracks repeated model/tool cycles and contributes to bounded execution. The
graph must never be allowed to loop indefinitely.

### `verification_error`

Records deterministic workflow failures, such as a missing result for a tool
call or an invalid tool-result contract. It is not used to implement order
business rules.

## Node responsibilities

### `call_model`

- Sends the current message history and available tool schemas to OpenAI.
- Adds the assistant response to graph state.
- Lets the model decide whether to answer or request one or more tools.
- Does not execute tools or decide business outcomes.

### `execute_tools`

- Reads every tool call from the latest assistant message.
- Parses the model-generated JSON arguments.
- Validates them with the existing Pydantic models.
- Injects the trusted `customer_id` from graph state.
- Calls the real functions in `tools/orders.py`.
- Adds one tool-result message for every tool call.

### `verify_results`

- Confirms that every requested tool call produced exactly one result.
- Confirms that every result follows the expected structured contract.
- Routes valid results back to `call_model`.
- Produces a safe deterministic failure for invalid internal results.

This node does not decide whether an order can be cancelled or modified. Those
rules remain exclusively inside `tools/orders.py`.

### Conditional routing

After `call_model`:

- tool calls present → `execute_tools`;
- no tool calls and final text present → `END`;
- iteration limit reached → safe failure and `END`.

## Conversation state and checkpoints

V1 stores conversations in a custom in-memory dictionary. V2 replaces message
history storage with LangGraph's in-memory checkpointer:

```python
from langgraph.checkpoint.memory import InMemorySaver
```

The existing API-level `conversation_id` will be passed to LangGraph as its
`thread_id`:

```python
config = {
    "configurable": {
        "thread_id": conversation_id,
    }
}
```

The external API remains unchanged:

```json
{
  "message": "The 123 one",
  "customer_id": 1,
  "conversation_id": "existing-conversation-id"
}
```

The application must still verify that a conversation belongs to the current
`customer_id`. A LangGraph `thread_id` identifies saved graph state; it is not
an authentication or authorization mechanism.

`InMemorySaver` is intentionally non-persistent. Conversation history is still
lost when the process restarts. Durable checkpointers remain out of scope.

## Separation of responsibilities

```text
LLM
  Chooses tools and writes user-facing language.

LangGraph
  Controls state transitions, routing, loops, and checkpoints.

Application orchestration
  Validates model output, injects trusted context, and executes tools.

Order tools
  Own business rules and mutate order state.

FastAPI
  Owns the HTTP contract only.
```

Neither the LLM nor LangGraph becomes the source of truth for order state.
Successful operations still require a successful result from the corresponding
business tool.

## Expected file changes

The exact structure may evolve slightly, but V2 should remain small:

```text
app/
├── main.py
├── agent.py          # public interface + graph construction/nodes
├── models.py
└── tools/
    └── orders.py    # unchanged business rules

tests/
├── test_tools.py
├── test_agent.py
└── test_graph.py    # graph state, routing, loops, checkpoints
```

A separate `graph.py` should only be introduced if `agent.py` becomes difficult
to read. V2 should not add folders or abstractions merely to imitate a large
production project.

## Testing strategy

Existing V0/V1 tests must continue passing conceptually. Tests using a mocked
OpenAI client must not call the network or spend tokens.

V2 adds tests for:

- `call_model` appending the assistant message to state;
- routing to `execute_tools` when tool calls exist;
- routing to `END` when the model returns final text;
- executing several tool calls from one model response;
- chaining dependent tool calls across graph cycles;
- injecting the authenticated `customer_id` rather than trusting model output;
- rejecting access to another customer's conversation;
- preserving history when the same `conversation_id`/`thread_id` is reused;
- starting with empty history for a new conversation;
- stopping safely when the graph reaches its execution limit;
- handling invalid arguments and malformed tool results without claiming
  success.

Real OpenAI integration tests remain separate and opt-in.

## Migration plan

1. Add LangGraph as a dependency.
2. Define `AgentState`.
3. Extract the current loop responsibilities into graph nodes.
4. Add conditional routing and compile the graph.
5. Run the graph with `ainvoke` while keeping `handle_message(...)` as the
   application's public interface.
6. Add `InMemorySaver` and map `conversation_id` to `thread_id`.
7. Migrate and expand tests.
8. Remove the custom `while` loop and custom conversation-message storage only
   after behavioral parity is verified.

## Definition of done

V2 is complete when:

- `agent.py` no longer contains the manual agent `while` loop;
- LangGraph explicitly controls model/tool routing;
- dependent and multiple tool calls still work;
- conversation history is managed through graph checkpoints;
- conversation ownership remains enforced;
- business logic remains unchanged in `tools/orders.py`;
- FastAPI's request and response contract remains unchanged;
- unit tests run without OpenAI network calls or token usage;
- integration tests remain optional;
- all tests pass.

## Still out of scope for V2

- New Customer Operations domains or tools.
- Real authentication.
- Persistent databases or durable checkpointers.
- Evals and quality metrics.
- RAG or policy retrieval.
- Human approval and interrupts.
- Multi-agent systems and subgraphs.
- Distributed workers, queues, Redis, or PostgreSQL.
- LangSmith or external observability platforms.
- Deployment, load testing, and cloud infrastructure.

## Future portability

LangGraph is an internal implementation detail. The project keeps its own
FastAPI contract, business tools, validation models, and `handle_message(...)`
boundary. If a later version replaces LangGraph with a custom workflow engine,
the change should be limited mainly to orchestration and state persistence,
without rewriting order business logic or the external API.
