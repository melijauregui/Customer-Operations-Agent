# V0 — Single agent + 3 tools

## Goal

Build an agent able to receive a customer's message about an order and decide, on its own (via tool/function calling), which action to take — no `if "cancel" in message` type rules. The cycle we're trying to understand:

```text
User
 ↓
LLM understands request
 ↓
LLM selects tool
 ↓
Application executes tool
 ↓
Tool returns result
 ↓
LLM interprets result
 ↓
Response to user
```

Core principle: **the LLM is never the source of truth**. If a tool returns `success: false`, the agent must never claim the action succeeded.

## Current architecture

```text
customer-agent/
│
├── app/
│   ├── main.py           # FastAPI — POST /chat
│   ├── agent.py           # tool-calling loop (LLM ↔ tools)
│   ├── models.py           # Pydantic schemas (HTTP + tool arguments)
│   ├── config.py           # OPENAI_API_KEY loading / OpenAI client
│   │
│   └── tools/
│       └── orders.py       # business logic + in-memory orders
│
├── tests/
│   ├── conftest.py          # fixture: resets in-memory state between tests
│   ├── test_tools.py         # unit tests for orders.py (no LLM)
│   ├── test_agent.py          # tool-calling loop tests with the LLM mocked
│   └── test_integration.py     # real test against OpenAI (separate, optional)
│
├── pytest.ini
├── requirements.txt
└── .env.example
```

- `main.py` has no logic of its own: it takes the message, passes it to the agent, returns the response.
- `agent.py` orchestrates the LLM → tool → LLM loop. It never decides business rules.
- `tools/orders.py` holds all the business logic (what's cancellable, date validation, etc.) and the "state" (an in-memory dict — no database yet).
- `models.py` validates both the HTTP contract (`ChatRequest`/`ChatResponse`) and the arguments the LLM sends for each tool, before they reach `orders.py`.

## Request flow

```text
POST /chat {"message": "Cancel order 123"}
        ↓
main.py calls agent.handle_message(message)
        ↓
1st call to the LLM, with the 3 available tools
        ↓
LLM responds: "I want to call cancel_order(order_id=123)"
        ↓
agent.py validates the arguments with Pydantic
        ↓
tools/orders.cancel_order(123) runs (real business logic)
        ↓
the tool returns {"success": true/false, ...}
        ↓
2nd call to the LLM, with that real result in the history
        ↓
LLM writes the final response based on the result (doesn't invent it)
        ↓
{"response": "Done, I cancelled your order 123."}
```

## Current limitations

- In-memory orders (a Python `dict`): lost on process restart. No database.
- No authentication or multi-tenancy: anyone hitting the endpoint can operate on any order.
- No conversation state: every request to `/chat` is independent — the agent doesn't remember previous messages.
- No handling of "missing information" (e.g. "I want to cancel my order" without saying which one) — that's V1.
- No frontend: tested via `curl`/Swagger.
- A single agent, three fixed tools: no multi-agent, RAG, or more complex orchestration.
- No quality metrics (tool selection accuracy, hallucination rate, etc.) — those come with V3's evals.
