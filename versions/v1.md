# V1 — Real conversations

## Goal

Handle messages where information is missing, by letting the agent look up the customer's own orders and by keeping conversation state across turns — instead of every request to `/chat` being fully independent, as it was in V0.

```text
User: "I want to cancel my order."
Agent: "Which one of your orders?"
```

## What's new compared to V0

- **A 4th tool: `get_customer_orders(customer_id)`.** Returns the list of orders belonging to a given customer, so the agent can look them up when the user doesn't give an `order_id`.
- **`customer_id` on `ChatRequest`.** There's still no authentication (out of scope until a later version) — `customer_id` is passed explicitly in the request body, simulating "the logged-in customer" without building real auth. Each order in `tools/orders.py` now also carries a `customer_id`.
- **Conversation state, still without a real database.** An in-memory dict `conversations: dict[str, list[message]]` (same pattern as `orders`: simple, non-persistent, lost on restart) keyed by a `conversation_id`. `ChatRequest` gets an optional `conversation_id`; if it's missing, the server creates a new one and returns it in `ChatResponse` so the client can continue the conversation.
- **The tool-calling loop stops being "2 fixed calls".** In V0, `agent.py` was hardcoded to: 1st call decides a tool (or not) → execute → 2nd call writes the final answer. That's generalized into a bounded `while` loop that keeps calling the model and executing tools until it responds with plain text, capped at a max number of iterations to avoid infinite loops.

## Conversation IDs

`customer_id` identifies the customer, while `conversation_id` identifies one
conversation belonging to that customer. A customer may have several independent
conversations at the same time.

- Omit `conversation_id` to start a new conversation. The server generates one
  and includes it in `ChatResponse`.
- Send the returned `conversation_id` in the next request to continue that
  conversation with its previous history.
- Omit it again to start another conversation without restarting the server.
- A conversation is permanently associated with the `customer_id` that created
  it. Another customer receives the same `conversation_not_found` behavior as
  an unknown conversation ID.

```json
{
  "message": "I want to cancel my order",
  "customer_id": 1
}
```

```json
{
  "message": "The 123 one",
  "customer_id": 1,
  "conversation_id": "the-id-returned-by-the-first-request"
}
```

In V1, conversation history is stored only in the application's memory. A
server restart removes all conversation IDs and their histories. The ID is a
routing mechanism for state, not an authentication credential.

## Why the loop can't stay at 2 fixed calls

It's not about the model asking for several tools *at once* — a single response can already request multiple tool calls, and the existing `for tool_call in assistant_message.tool_calls` executes all of them in one round, so 2 calls is enough for that case.

The real issue is **sequential, dependent tool calls**: when the arguments for the next tool call can only be known after seeing the result of a previous one, within the same user turn, without asking the user anything in between. For example:

- *"Cancel the order arriving on August 20th"* — the model doesn't have an `order_id`, only a description. It needs to: call `get_customer_orders(1)` (supposing customer_id=1) → see that order 456 is the one delivering on 2026-08-20 → only then call `cancel_order(456)` → answer. That's 3 LLM calls (2 tool rounds + 1 final), all in the same turn.
- *"Cancel my order"* when the customer only has one order — instead of asking "which one?", the agent can call `get_customer_orders(1)`, see there's only one, and call `cancel_order(that_id)` directly. Same two-round chain.

With a hardcoded 2-call loop, that second round is impossible to express: the only thing the model can do after a tool result is "give the final answer", never "look at the result and decide it needs another tool first." The bounded `while` loop doesn't change behavior for the simple V0 cases (those still resolve in 2 round trips) — it just stops assuming 2 is always enough.

## Request flow example (two turns)

```text
Turn 1:
  User: "I want to cancel my order" (customer_id=1, no conversation_id)
        ↓
  LLM sees the order_id is missing -> calls get_customer_orders(1)
        ↓
  Agent: "You have order 123 (processing) and order 456 (shipped). Which one do you want to cancel?"
        ↓
  response includes conversation_id="abc123"

Turn 2:
  User: "The 123 one" (customer_id=1, conversation_id="abc123")
        ↓
  the previous history is already stored in memory (keyed by conversation_id)
        ↓
  LLM calls cancel_order(123)
        ↓
  Agent: "Done, I cancelled your order 123."
```

## Still out of scope for V1

- No real authentication — `customer_id` is trusted as-is from the request body.
- No persistence — `orders` and `conversations` are both in-memory dicts, lost on restart.
- No LangGraph / explicit state machine — the loop is still a plain bounded `while`, not a graph with named nodes (that's V2).
- No evals / accuracy metrics for the new multi-step behavior (that's V3).
